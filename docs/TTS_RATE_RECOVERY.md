# 1.0.9 在线朗读异常恢复核查

## 日志能确认什么

对照 1.0.9+10028 源码，`online_tts.dart:170/173` 分别为原生播放器 `stop` / `dispose`；`:540` 是停止流程调用清理；`:577` 是 `next()` 停止当前播放；`tts_handler.dart:196` 是“下一段”。服务切换也调用同一清理链路。

旧版清理按顺序执行，异常会提前退出，跳过清空播放器引用和缓冲区。随后的下一段、停止、切换语音会再次碰到同一个异常播放器。这可以解释“第一次出错以后整个朗读都不能用了”，但日志未保留原生错误码/消息及语速数值，不能确认首次原生异常由哪个语速触发。

语速修改本身不重启 OnlineTts 的播放器，而是清空待播放音频并变更请求版本。原滑块每次移动都触发这一操作；旧版本请求失败后还可能继续重试，造成不必要的请求及等待。日志中的 Edge 语音列表网络错误属于另一条链路。

## 本地修复

- 滑块拖动只预览语速/音调，松手后提交；当前句继续播放，后续句子重新生成。相同值和非法数值不触发在线语音重新请求。
- 丢弃旧参数音频及旧请求异常，不再为已失效的参数继续重试。
- 清理先解除播放器引用，单项原生清理失败不阻断剩余清理。初始化成功后才缓存播放器；失败恢复时重新创建播放器。
- 暂停/恢复的原生异常转成可重试状态，保留当前句；恢复播放后仍可再次暂停/继续。
- 连续切换服务串行清理。停止或后续导航会使之前待完成的导航失效，防止停止后自动重新朗读。
- 调速请求失败日志不记录书籍片段或原始服务错误内容。

## 验证范围

`tts_rate_recovery_test.dart` 使用可控请求和模拟原生播放器，覆盖旧语速请求成功/失败、当前句不中断、初始化/播放/暂停/恢复失败、连续导航与停止、服务切换释放失败等 11 个场景。TTS 与 AI 阅读错误组件回归合计 61 项通过，1 项跳过。

以上是自动化验证，不是 vivo V2301A 真机复现。修复纳入 1.1.0+10029；已安装的 1.0.9 需要升级后才包含这些代码修改。
